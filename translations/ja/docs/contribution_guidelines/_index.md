## Jumpstart コントリビューションガイドライン

**Arc Jumpstart コントリビューションガイドラインへようこそ！**

Arc Jumpstart への貢献をご検討いただき、心より感謝申し上げます。あなたの献身は非常に価値あるものです！私たちの Jumpstart リポジトリは、高品質で細部にわたる自動化とドキュメントのバンドルで成り立っています。

これらのガイドラインを、私たちの基準に合致した成功した洗練されたコントリビューションを作成するためのロードマップとして使用してください。初めての方には、承認されたシナリオ形式についての貴重な洞察を提供し、ここで概説されているすべてのガイドラインを網羅する既存のシナリオの生のコードを探ることをお勧めします。ご質問がある場合は、Arc Jumpstart プロジェクトメンテナーのチームがサポートします。

コントリビューションを歓迎しており、AI 支援のドキュメントを拡張または編集する際は、すべてのコントリビューターがこれらのガイドラインに留意することを奨励します。

## コードレビュー

Arc Jumpstart は、さまざまな自動化スクリプトと技術、コードスタイル、ドキュメントの組み合わせです。

何かが公開される前に、Jumpstart のコアメンテナーの 1 人によってコードレビューが行われます。あなたのコントリビューションが広く採用され、可能な限り最高の基準を満たすことを望んでおり、そこに到達するお手伝いをします！

## Issue、プルリクエスト、ディスカッション

コントリビューションに着手する前に、オープンソースコミュニティ内で明確なコミュニケーションを確立することが重要です。コラボレーションを合理化し、透明性を維持するために、コントリビューターが提案した変更作業を開始する前に、[Issue を開いて](https://aka.ms/JumpstartIssue) ディスカッションを開始するか、[プルリクエスト（PR）](https://aka.ms/JumpstartFeature) を行うことをお願いしています。Issue を開くことで、提案されたアイデアに関するディスカッションとコンセンサス形成が可能になり、それがプロジェクトの目標と既存の作業に合致していることを確認できます。

[GitHub Discussions](https://aka.ms/JumpstartDiscussions) は、コミュニティメンバーが会話に参加したり、質問したり、アイデアを共有したりするためのインタラクティブなプラットフォームを提供する追加の手段です。プルリクエストは実装したい変更を示す具体的な提案です。このプロセスに従い GitHub Discussions を活用することで、アイデアが共有、レビュー、集合的に改良される協力的な環境を育成し、プロジェクトの継続的な改善を確保します。これらのガイドラインへの積極的な参加と遵守が、私たちの協力的な取り組みの成功に不可欠です。

## コードの配置

プルリクエスト（PR）を提出する前に、フォルダ構造内のコードとドキュメントの配置についてプロジェクトメンテナーの 1 人に相談することをお勧めします。メンテナーはプロジェクトのアーキテクチャと組織を深く理解しており、コントリビューションが既存のコードベースとシームレスに統合されるようにします。彼らのガイダンスを求めることで、変更がどこに最も適合するかについて情報に基づいた決定を下すことができます。メンテナーとの協力は、あなたの努力がプロジェクトのビジョンに合致することを確保するだけでなく、オープンソースコミュニティの成功に不可欠な協力的な精神を育みます。ぜひご連絡ください。プロジェクトに積極的な影響を与える意味のあるコントリビューションをするお手伝いをします。

## 既存のドキュメントとコードへの依存

私たちの協力的なオープンソース環境では、一貫性と確立されたガイドラインへの遵守を重視しています。コントリビューションがプロジェクトの目標に合致し、プロジェクトの整合性を維持することを確保するために、長年の集合的な知識を体現する既存のドキュメントとコードに依存することを強くお勧めします。これには、微妙なベストプラクティス、コーディング標準、プロジェクト固有の規則が含まれます。

既存のリソースへの依存に関するガイドライン:

1. **ドキュメント:** 新しいドキュメントを起草する前に、好ましいライティングスタイル、フォーマット、コンテンツ構造を理解するために既存のドキュメントを徹底的に探索してください。ギャップや不正確な箇所を見つけた場合は、自由に既存のドキュメントを更新・改善してください。

2. **コードベース:** 既存のコードベースを調査して、プロジェクトのアーキテクチャ、コーディングパターン、コーディングスタイルを把握してください。プロジェクト全体の一貫性を維持するために、既存のコーディング習慣を模倣してください。新しい機能や変更を導入する必要がある場合は、既存のコードのロジックと構造に合致していることを確認してください。

## 前提条件のガイドライン

すべての Jumpstart シナリオまたはソリューションは、シームレスなユーザーエクスペリエンスの基盤を設定する包括的な「前提条件」セクションから始まる必要があります。次のガイドラインに従ってください:

1. **自動化の優先度:** 自動化できる前提条件を識別することに慎重を期してください。前提条件が自動化フローに組み込める場合は、シナリオ内にシームレスに統合し、ユーザーの利便性を高め、手動介入を最小化する必要があります。

2. **レビュアーの洞察:** プルリクエストのコードレビュープロセス中のフィードバックとレビュアーの意見を受け入れてください。レビュアーには貴重な専門知識があり、特定の前提条件を自動化する機会を特定できる場合があります。これらの提案への対応力は、コミュニティの協力的な精神を豊かにします。

3. **既存シナリオの参照:** 前のセクションで強調したように、既存のシナリオを参照することを強くお勧めします。確立されたテンプレートからインスピレーションを得ることは、一貫性を促進するだけでなく、将来のリファクタリングや不必要な変更の可能性を減らします。これらの参照をスキャフォールドとして使用して、シナリオのための堅牢で効率的な前提条件を構築してください。

## Markdown リントとスタイルガイドライン

コンテンツのプロフェッショナルなプレゼンテーションと読みやすさを維持するために、すべてのシナリオと README ファイルが標準の Markdown とリントルールに準拠していることが不可欠です。次のガイドラインに従ってください:

1. **標準 Markdown の使用:** コンテンツが標準の Markdown 構文に従っていることを確認し、読者に対して均一性と理解しやすさを保証します。

2. **エディターの推奨:** 編集のニーズには [Visual Studio Code (VS Code)](https://code.visualstudio.com/) の使用をお勧めします。VS Code は、Markdown 編集に特化した拡張機能のサポートによって強化された堅牢な統合開発環境（IDE）エクスペリエンスを提供します。

3. **Markdown リント:** 新しいまたは更新されたシナリオのプルリクエスト（PR）を提出する前に、徹底的な Markdown リントを実施してください。このプロセスはエラーを特定して修正し、ドキュメントの正確さとプロフェッショナリズムを確保します。VS Code をエディターとして選択する場合は、[_markdownlint_](https://marketplace.visualstudio.com/items?itemName=DavidAnson.vscode-markdownlint) 拡張機能をインストールすることを強くお勧めします。この拡張機能はリントプロセスを合理化し、Markdown 関連の問題やタイポを効率的かつ効果的に特定できます。

### Markdown リントの例と解決ガイドライン

エラーのないドキュメントを確保するために、シナリオを書く際に発生する可能性のある一般的な問題とその解決方法に慣れてください。ここでは、リント拡張機能によってフラグされた Markdown ルールと、違反を修正するためのステップバイステップの指示を説明します。

1. **見出し構造:** 見出しの適切な階層を確保してください。Markdownlint は見出しレベルの不整合をハイライトする場合があります。解決するには、ハッシュ記号（#）の数を希望する見出しレベルに合わせて調整してください。

2. **リンクのフォーマット:** Markdownlint は不正または壊れたリンクを検出します。リンクが正しくフォーマットされていること（リンクテキストの角括弧と URL の括弧の両方を含む）を確認してください。正しい URL を提供することで壊れたリンクを修正してください。

3. **リストのフォーマット:** 一貫したリストのインデントと箇条書きスタイルを維持してください。Markdownlint はミスアライン、または不適切にフォーマットされたリストを特定するのに役立ちます。解決するには、リストアイテムを正しく整列させ、一貫した箇条書きまたは番号を確保してください。

4. **コードブロックのインデント:** Markdownlint はコードブロックが正しくインデントされていることを確認します。コードブロックがフラグされた場合は、周囲のテキストに合わせてインデントを調整してください。これにより、コードの読みやすさとプレゼンテーションが向上します。

5. **画像の構文:** 画像を含める場合、Markdownlint は構文をチェックします。画像リンクが正しくフォーマットされていること（代替テキストを角括弧で囲み、画像 URL を括弧で囲む）を確認してください。画像を正しく表示するために構文エラーを修正してください。

## スクリーンショットの品質と基準

スクリーンショットの卓越した品質、正確さ、清潔さは、優れた Jumpstart シナリオと読者体験を提供するために最も重要です。次のガイドラインに従ってください:

1. **明確さと精度:** スクリーンショットが明確で鮮明であり、説明するコンテンツを正確に表していることを確認してください。高解像度の画像は読者の視認性と理解を高めます。

2. **関連性とコンテキスト:** シナリオのステップに直接関連し、必要なコンテキストを提供するスクリーンショットをキャプチャしてください。関連性のないまたは余分なビジュアルは読者を混乱させ、教育的な価値を薄める可能性があります。

3. **外観の一貫性:** ドキュメント内のすべてのスクリーンショット全体で一貫したビジュアルスタイルを維持してください。一貫性はシナリオのプロフェッショナルな外観を高め、まとまりのある読書体験を促進します。

4. **注釈とハイライト:** 必要に応じて、スクリーンショット内の特定の要素に注意を引くための注釈またはハイライトを使用してください。矢印、円、またはテキストのコールアウトは読者の焦点を誘導し、重要な詳細を強調できます。

5. **ドキュメントの編集:** プロセスの重要なステップとして、スクリーンショットがドキュメントにシームレスに統合されていることを確認してください。フォーマット、配置、キャプションに注意を払い、洗練されたまとまりのあるビジュアルナラティブを作成してください。

6. **解像度とフォーマット:** PNG や JPEG などの一般的に使用される画像フォーマットを選択し、適切な解像度を確保してください。画像が大きすぎるとドキュメントの読み込み時間が遅くなる可能性があるため、品質とファイルサイズのバランスを取ってください。

7. **アクセシビリティ:** 視覚障害を持つ読者を考慮してください。注釈を使用する場合は、すべてのユーザーのアクセシビリティを確保するために、スクリーンリーダー用の代替説明を提供してください。

## コードブロックとコマンドのフォーマット

Jumpstart では、コードブロックとコマンドは技術情報を正確に伝える上で重要な役割を担っています。Markdown ルールへの遵守とシナリオ基準の維持を確保するために、各コードブロックとコマンドが正しい Markdown 言語ハイライターを使用することが不可欠です。

1. **Markdown 言語ハイライター:** 各コードブロックとコマンドに適切な Markdown 言語ハイライターを選択してください。Markdown はさまざまなプログラミング言語とスクリプトフォーマットをサポートしています。正しい言語ハイライターを指定することで、構文ハイライトが有効になり、コードの読みやすさと理解が向上します。

2. **シナリオ全体の一貫性:** すべてのシナリオ全体で Markdown 言語ハイライターの一貫性を維持してください。一貫したフォーマットにより、さまざまなシナリオを移動するユーザーにシームレスな読書体験が作成されます。

3. **コマンドライン入力:** コマンドライン入力を提示する場合は、コマンド構文を正確に表すために適切なシェル言語ハイライター（例: Bash、PowerShell）を使用してください。適切にフォーマットされたコマンド例により、ユーザーは予期しないエラーに遭遇することなく手順を再現できます。

4. **編集とレビュー:** 編集とレビューのプロセス中に、コードブロックのフォーマットに細心の注意を払ってください。レビュアーとコントリビューターは、正しい言語ハイライターが各コードスニペットとコマンドに適用されていることを確認するために協力し、正確さと一貫性のためにコンテンツを洗練させます。

## 認証情報、シークレット、パスワードの管理

認証情報、シークレット、パスワードを保護することの重要性はいくら強調してもし過ぎることはありません。シナリオのコードとガイドを作成する際には、機密情報を保護するために最大限の注意が必要です。このようなデータの安全な取り扱いを確保するための重要なガイドラインを以下に示します:

1. **機密情報のマスキング:** コードに含まれる認証情報であれ、ターミナル出力の一部として表示されるシークレット/パスワードであれ、これらの詳細を読者からマスクすることが不可欠です。マスキングにより、機密情報が機密のまま保たれ、不正な個人がアクセスできなくなります。

2. **環境変数:** 機密情報の保存に環境変数の使用を奨励してください。環境変数を使用することで、認証情報とシークレットをコードベースの外で安全に管理でき、バージョン管理システムでの偶発的な公開のリスクを減らします。

3. **暗号化とハッシュ:** 可能な限り、機密データを保護するための暗号化とハッシュ技術を提唱してください。パスワードと機密設定ファイルを暗号化することで、保存された情報へのアクセスを難しくし、悪意ある主体から保護するための追加の層を追加します。

4. **教育的コンテキスト:** 教育目的で認証情報またはシークレットに関わる特定の操作を示す必要がある場合は、表示された情報が指導目的のみであり、実際のシナリオでは適切な値に置き換えられるべきであることを明確にハイライトしてください。

5. **定期的なレビュー:** レビュープロセス中は、機密情報に関わるコードに細心の注意を払ってください。レビュアーとコントリビューターは、機密の詳細が適切にマスクされ保護されていることを確認するために協力し、シナリオのコンテンツが厳格なセキュリティ基準を満たしていることを確認します。

認証情報、シークレット、パスワードを保護することにより、Jumpstart シナリオの全体的なセキュリティを強化していただきありがとうございます。

## 命名規則とブランドガイドライン

Jumpstart の領域では、技術用語、ブランド名、およびさまざまな識別子の正確な命名規則と正確な表現が不可欠です。会社名、製品、機能、その他の技術的な用語の書き方における一貫性と明確さは、ドキュメント全体のプロフェッショナリズムとコヒーレンスを維持するのに役立ちます。次のガイドラインに従ってください:

1. **一貫したスペルと大文字化:** ドキュメント全体で会社名、製品、機能の一貫したスペルと大文字化を確保してください。

2. **公式ブランドガイドライン:** 企業や組織が提供する公式ブランドガイドラインに精通してください。指定された命名規則、商標、およびロゴに従ってください。商標付きの用語を尊重し、それぞれの主体が定めたガイドラインに従って使用してください。

3. **頭字語と略語:** テキストで使用する前に頭字語と略語を明確に定義して紹介してください。紹介後は、混乱を防ぐために略語形式を一貫して使用してください。

4. **技術用語:** 技術用語を扱う際は、適用可能な場合は業界標準の名称を使用してください。普遍的に理解されない可能性のある専門用語や略語は避けてください。専門用語が必要な場合は、読者がコンテキストを理解できるよう明確な説明を提供してください。

5. **バージョン番号:** ソフトウェア製品やツールを参照する際は、議論されている特定のバージョンを示すためにバージョン番号を含めてください。この情報は、読者がドキュメントをソフトウェア環境と正確に照合するために不可欠です。

6. **コード内のブランディング:** コードスニペットや設定例にブランド固有の要素が含まれる場合は、コード内の命名規則が公式ブランドガイドラインと一致していることを確認してください。テキストの説明とコード例の間の一貫性が重要です。

7. **レビューと協力:** レビュープロセス中に命名規則とブランディングに注意を払ってください。レビュアーとコントリビューターは、すべての名前と用語が正確に表現されていることを確認するために協力する必要があります。
